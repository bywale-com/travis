# How to read a plate when we build

**Seat:** Product Manager.  
**Why:** Om Coda protocol (Tower specimen). Once a pocket is locked, read the image for what we **did not say** but the build still has to do — and for what is **in the picture but out of this build**.  
**Flag:** [`PHASE-ONE-LOG.md`](./PHASE-ONE-LOG.md) Current — do not overwrite founder wording.  
**Generate** (before this file): [`PLATE-CHROME-RULE.md`](./PLATE-CHROME-RULE.md) — screenshot the live desk, lock chrome, paint only the pocket.  
**With:** This file says what the engineer does with a locked pocket. FACE files name the glass; packets fill the five buckets.

Do not invent a thirteenth bucket. These five are the read.

---

## Five buckets

The plate is one state of one example. Literal reading misses the product.

| Bucket | What it is | What you do |
|--------|------------|-------------|
| **1. Copy** | Inside **this** pocket. We talked about it. It is on the glass. | Build it. |
| **2. Do not build** | On the glass. Example furniture, teaching caption, remnant of a dead revision, stale nest. | Do not freeze it as the system. |
| **3. Implied** | A **control** is on the glass. We never discussed it. It still has to **work**. | Build the function. Same data, that control. |
| **4. Completes** | Not this state of the PNG. The module is unfinished without it. | Build it. No extra PNG. |
| **5. Out of scope this build** | On the PNG, **outside this pocket**. Other modules, parked next work. | Do not rebuild the whole product from this packet. |

Teaching scenery on a nested plate/image is always bucket 2 unless the packet says that content *is* the product.

---

## Packet rule

When we lock a pocket, the packet fills buckets 1–5 **in that order**. Founder comments stay in the packet. Do not wait for a second chat to notice implied controls or the other value of a state.

Paste blocks for **Engineer** and **Systems Analyst** live in the packet so nothing is lost in seat transition.
